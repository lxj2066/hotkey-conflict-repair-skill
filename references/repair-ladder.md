# 修复阶梯：哪些能代劳，哪些只能指路

> 原文设想的四级阶梯里，「系统层直接释放他人热键」这一级做不到。本文件写清每一级的真实边界，
> 免得把引导包装成自动执行。**能力边界说在前面，用户才不会觉得被骗。**

## 定级标准

按「系统能代劳的程度」分，不按「修复效果好不好」分。

| 级 | 动作 | 本包能做到 | 谁动手 |
|---|---|---|---|
| L0 | 探测哪些键被占 | 全自动 | 脚本 |
| L1 | 进目标软件设置关掉那组键 | 只给点击路径，一步一步 | 用户 |
| L2 | 关驱动软件的全局宏总开关 | 只检测驱动在不在跑，给出开关位置 | 用户 |
| L3 | 用 PowerToys 拦掉冲突组合 | 生成可导入的配置片段，用户导入 | 用户（半自动） |
| L4 | 多个软件都想留，选一个 | 出单选表，记住选择，修完复测 | 用户 |

## 为什么 L1 不能自动做

要在系统层释放**别的进程**注册的热键，只有两条路：把代码注入目标进程去调 `UnregisterHotKey`，或者写内核驱动去改热键表。OpenArk 那类工具走的就是前一条。

两条路对本包都不成立：注入会被杀软拦、会被平台判为恶意行为；写驱动要签名、要用户装驱动。为一个「截图键不好使」的问题让小白装内核驱动，是拿系统稳定性换便利。

所以正确做法是：**把「去哪一步点哪里」说到位**，让用户 30 秒点完，而不是让他自己去软件里翻。知识库每条候选都带 `fix` 字段，就是这个点击路径。

用户话术：「这一步得你自己点一下，因为它要改的是微信自己的设置，改别的软件的配置文件容易把软件弄坏。路径是……」

## 为什么 L2 只能指路

G HUB、雷云、iCUE 都没有公开的命令行接口去开关全局宏。查到的总开关位置写在 `assets/hotkey-catalog.json` 的 `drivers` 里，报告里直接给这一句。

用户话术：「鼠标乱打字是驱动里的宏在跑。打开 G HUB → 宏 → 设置 → 把底部那个全局开关关掉，所有侧键宏立刻停，不用一个个删。」

## L3 的边界

PowerToys Keyboard Manager 能拦组合并映射成「无操作」。但它运行时会持有自己的配置，直接改它的 `settings.json` 会被覆盖，所以本包**只生成片段让用户导入**，不直接写它的配置。

而且这一级只在两种情况下值得用：目标软件拒绝改自己的键，或者冲突来自查不到来源的钩子。能用 L1 解决就别上 L3，多装一个常驻工具是新的负担。

## L4 什么时候才出表

只有一种情况：**有多个软件都该保留这组键，系统无法替用户判断意图**。

出表规则（写死在 `scripts/hk_plan.py`）：

1. 一行一个组合键，只保留三列：快捷键、保留哪个程序、当前状态。
2. 默认勾选上次的裁决；没有记录就按候选置信度勾。
3. 单选。用户选第二个时不做拦截，但报告只认一个。
4. 系统保留键整行标灰，不给单选。
5. 表里出现「疑似」字样，因为探测只能证明被占，不能证明是谁。

表出现得越少越好。目标是把 L0 到 L3 能收敛的问题全部收敛掉，只把真正需要人的意图的那一小部分送到用户面前。

## 降级顺序

L1 走不通 → L3（拦掉）→ 仍走不通 → 建议换一个没人用的组合（`safe_keys`）。L2 只针对鼠标宏，与 L1 平行，不互相替代。L4 不降级，它本身就是最后一步。

## 一句总纲

本包自动完成「查清楚」，人工完成「点一下」。把这两件事说混，用户第一次用完就不会再用第二次。
